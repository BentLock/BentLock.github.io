ARTEX 동작 원리 분석

2026.10, 시큐아이 개별 업무, 분석 보고서 PDF

선행연구로 화이트박스 취약점 탐색 파이프라인을 만든 뒤, 여러 AI 에이전트가 스스로 침투테스트를 수행하는 오픈소스 도구 ARTEX를 분석해 보고서로 정리했습니다. 둘 다 AI로 취약점을 찾고 검증하지만 전제가 다릅니다. 제 파이프라인은 소스코드를 읽는 화이트박스 방식이고, ARTEX는 실행 중인 서비스에 요청을 보내며 단서를 찾는 블랙박스 방식입니다.

분석한 내용

  • 방향을 정하는 planner와 명령을 실행하는 worker가 일을 나누는 구조, 사람이 목표와 제약을 바꿀 때의 전달 경로
  • 발견한 대상, 관찰한 사실, 재현한 취약점을 서로 다른 기록으로 남기고 그래프로 잇는 방식
  • 다시 계획하거나 검사를 멈추는 조건, 목표 달성을 판정하는 기준

느낀 점

작업이 길어질수록 커지는 컨텍스트를 저는 후보와 단계로 잘게 나눈 JSON으로 다뤘는데, ARTEX는 조사 대상과 가설, 결과를 그래프로 연결해 같은 문제를 풀었습니다. 같은 문제를 전혀 다른 구조로 해결한 점이 인상 깊었습니다.

또 블랙박스 진단 방법론을 잘 몰랐던 제게는 ARTEX가 판단하는 과정 자체가 공부가 되었습니다. 시험한 값으로 결론이 나지 않으면 입력 위치를 바꿔 다시 시도하고, 순차 요청이 막히면 동시 요청으로 방법을 바꾸고, 비교할 기준이 없는 검사는 멈추는 흐름을 따라가며 블랙박스에서 가설을 세우고 검증하는 순서를 익혔습니다.

LLM 에이전트 구조 분석, Go 소스코드 분석, 기술 보고서 작성

가정용 공유기 0-day 탐색

약 2개월, 6인 팀, K-Shield 주니어

TOTOLINK X5000R, X6000R 펌웨어를 에뮬레이션 환경에서 분석해 팀이 0-day 3건을 찾았고, MITRE에서 CVE 3건을 받았습니다.

제가 맡은 일 중 가장 기억에 남는 것은 인증 조건을 다시 확인한 일입니다. 처음에는 로그인 없이 공격되는 취약점으로 보였습니다. 인증 로직을 끝까지 따라가 보니, 에뮬레이션 환경에서 세션 토큰이 비어 있어 비교가 통과된 것이었습니다. 이 원인을 밝혀 인증이 필요한 취약점(PR:L)으로 정리하는 데 기여했습니다.

요청을 처리하는 함수(sub_40BCB8)는 이 함수가 거짓을 돌려주면 "token invalid"로 요청을 거부합니다. 비교 대상인 세션 ID는 로그인할 때 만들어지는 /var/cste/temp_status 파일에서 읽는데, 에뮬레이션 환경에서는 로그인 과정이 돌지 않아 이 파일이 없었습니다. 실제 기기에서는 이 파일이 있어 올바른 토큰이 필요하므로, busybox 셸에서 세션 파일을 직접 만들어 실제 기기와 같은 조건에서 공격을 진행했습니다.

펌웨어 에뮬레이션, QEMU, 정적 분석
